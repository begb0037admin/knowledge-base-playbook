AI Knowledge Base Playbook

A complete record of how an AI-powered, voice-enabled knowledge base was built for HR - and everything needed to replicate it elsewhere.

July 2026 University of Oxford, HR Systems v1.0 - first edition
Section 1

Introduction

This document records - in full - how an AI-assisted knowledge base was designed, built, debugged, and populated for the HR Functional Analysis team at the University of Oxford. It exists so that the lessons learned over many months of iteration are not lost, and so that the same system can be stood up for other departments or organisations without repeating the same pain.

The system lets a staff member ask a plain-English question - typed or spoken - and receive a precise, cited, step-by-step answer drawn from 2,515 source documents across three data sources: the Access Group PeopleXD help centres, 567 PDFs (SharePoint library and Salesforce-hosted step-by-step guides), and internally authored guides. It requires no training, no searching through folders, and no specialist knowledge of where information lives.

Section 2

What Was Built

The knowledge base is a static single-page web application. It has no server, no database, and no ongoing infrastructure costs beyond a Cloudflare Worker (free tier). Everything is hosted on GitHub Pages.

The user experience

A staff member opens the site. There is one input: a question box. They type (or speak) a question in plain English - "How do I process a leaver in PeopleXD?" or "What are the steps to configure pension by appointment?" The system retrieves the most relevant documents using BM25 search, then passes those documents to Claude (via a Cloudflare Worker) to generate a step-by-step answer with direct source links. There is also a voice agent mode (Talk button) for fully spoken interaction.

AI card summarisation (two-level)

Every card in the document library shows a short summary when collapsed and a longer, more detailed summary when expanded. Rather than truncating the full document text (which cuts off mid-sentence and reads as an arbitrary excerpt), a dedicated script calls Claude twice per document to generate two purpose-written summaries:

FieldLengthPurpose
ss (short summary)3-4 sentencesCollapsed card preview - what the document covers, what task it helps with, when to open it. Written so a reader scanning the list can judge relevance without expanding.
sl (long summary)6-10 sentencesExpanded card detail - specific steps, menu paths, field names, error scenarios, and who uses the document. Grounded only in what the source text actually contains - never invents detail.

The original capped excerpt (field s) is never modified or removed - the two new fields sit alongside it, and the dashboard falls back to s for any document that hasn't been enhanced yet. This makes the rollout safe to run in batches over multiple sessions without ever leaving the site in a broken state.

✓

Rollout completed 10 July 2026. All 2,515 documents across all five sources (Change Management, How To Guides, Access Group PDF guides, Access Group web articles, Kevin's Guides) now have both fields. See Section 10 for two operational incidents encountered during the rollout and the lessons drawn from them.

Technology Stack

Every technology choice here was made for a reason - and some choices were made after other approaches were tried and failed. The "why" is recorded alongside the "what."

TechnologyRoleWhy this choice
Playwright (Python)Web scrapingThe scraping target (Access Group / Intercom) requires JavaScript rendering and authenticated sessions. Playwright provides a real browser context, handles login flows, and - critically - can intercept native file download events (page.expect_download()), which was essential for Salesforce-hosted PDFs.

Section 5

Data Sources

Access Group Help Centres

The Access Group (PeopleXD vendor) publishes help documentation across eight module-specific help centres, each hosted on Intercom. Articles are rendered as JavaScript-heavy pages - standard HTTP fetching returns an empty shell. Playwright navigates each article, finds the PDF download link where one exists, falls back to rendering the page to PDF when not, and saves to per-module subfolders.

PeopleXD Module Guide PDFs

Separate from the help centres, Access Group publishes detailed step-by-step user guides indexed in 11 "guide index" articles. Each guide is hosted on Salesforce (accessgroup.my.salesforce.com) behind a file viewer page. These require an authenticated Salesforce Community session to download. See Section 9 for the full story of how this was solved.

SharePoint documents

Internal "How To Guides" and Change Management documents, exported from SharePoint as a zip file. The extract_sharepoint.py script unpacks these into the library/ folder and the index builder picks them up. This is a manual process: re-export the zip, replace the release asset, trigger the indexing workflow.

i

Adapting for other departments The SharePoint export method works for any team whose documents live in SharePoint. The help-centre scraper is specific to Access Group / Intercom - a different HRIS vendor will need different selectors. The guide PDF approach (Salesforce viewer + expect_download()) is general and will work for any Salesforce Community file hosting.

Section 6

Authentication

Access Group portal login

The scraper logs into accessgroup.my.site.com/Support/s/login/ using credentials stored as GitHub Actions secrets (ACCESS_USERNAME, ACCESS_PASSWORD). The authenticated Playwright session is then used for all subsequent requests. Cookies carry across to the Salesforce CDN domain (accessgroup.my.salesforce.com), which is the same Salesforce org.

Without login (--no-login flag), the public help-centre articles are still accessible. Guide PDFs are not - Salesforce returns 200 OK with an HTML redirect page, not a PDF.

No secrets in code or config files - ever. All credentials are stored in Cloudflare Worker secrets or GitHub Actions secrets. A secret committed to a public repo will be automatically revoked by GitHub within minutes, and the knowledge base will go dark.

Section 7

Build Guide - Replication from Zero

This section documents how to stand up an identical system for a new department or organisation. Assume the new team uses the same HRIS (PeopleXD / Access Group) and has SharePoint documents. Variations are noted where relevant.

Prerequisites

  • A GitHub account (free)
  • A Cloudflare account (free tier sufficient)
  • An Anthropic API key
  • An ElevenLabs API key (optional - for TTS/voice agent)
  • Access Group portal credentials (for guide PDF harvest)
  • A GitHub Actions runner (self-hosted) that has outbound internet access to the Access Group portal and Salesforce CDN
i

Why self-hosted runner? The scraper runs Playwright (Chromium) against authenticated web sessions. GitHub-hosted runners are ephemeral and have no persistent session. A self-hosted runner persists, is on your own network, and can run jobs up to 300 minutes - necessary for a full corpus harvest.

1

Fork or clone the template repository

Create a new repository from begb0037admin/hr-fa-knowledge-base. This contains the scraper, index builder, workflow, and front end. Remove or empty data/kb.json, data/kb-index.json, and downloads/ - these are environment-specific and will be regenerated.

2

Configure GitHub Pages

In the repo settings → Pages, set the source to main branch, root. GitHub will assign a *.github.io URL. Optionally set a custom domain via CNAME.

3

Set GitHub Actions secrets

In Settings → Secrets and variables → Actions, add: ACCESS_USERNAME and ACCESS_PASSWORD (your Access Group portal credentials).

4

Register a self-hosted runner

In Settings → Actions → Runners, add a new self-hosted runner. Follow the GitHub instructions to install and start the runner agent on a machine that has Chromium, Python 3.9+, and outbound internet access. The runner must be kept running as a service.

5

Update GUIDE_INDEX_ARTICLES in the scraper

In scrapers/access_group_scraper.py, update the GUIDE_INDEX_ARTICLES constant to the 11 guide index article URLs for your instance of PeopleXD. These are the Intercom articles that list links to individual module guides. The URLs are help-peoplexd.theaccessgroup.com/en/articles/....

6

Deploy the Cloudflare Worker

Create a new Worker in Cloudflare. Copy worker/worker.js into it. Add Worker secrets: ANTHROPIC_API_KEY, ELEVENLABS_API_KEY. Set the ALLOWED_ORIGIN environment variable to your GitHub Pages URL (e.g. https://yourdomain.github.io/your-kb). Note the Worker URL - you'll need it in the next step.

7

Update index.html with your Worker URL

In index.html, search for hr-kb-ai.kevinlelitte.workers.dev and replace with your Worker URL. Commit and push to main.

8

Run a diagnostic scrape first

Trigger scrape-help-centres.yml with diagnostic=true and login=true. This runs one guide per module, skips the index build, and uploads to a downloads_diag/ artifact - it cannot touch any production data. Review the logs: look for SF landed: lines (confirm authentication worked) and Download captured via: lines (confirm the PDF download mechanism works). Only proceed to a full harvest once the diagnostic is clean.

9

Run the full harvest

Trigger scrape-help-centres.yml with: login=true, guides_only=true (or guides=true, deep=true for the full corpus), limit=0, diagnostic=false. This will run for 20-60 minutes depending on corpus size. The workflow will automatically build the index and commit data/kb.json and data/kb-index.json to main.

10

Verify the document count

Never trust the green tick alone. After the workflow completes, fetch data/kb.json and count the array length: python3 -c "import json; d=json.load(open('data/kb.json')); print(len(d))". The number should reflect all your sources. If it is unexpectedly low, check the errors log in the workflow artifact.

Section 8

Workflow Configuration

The scrape-help-centres.yml workflow has several inputs that control its behaviour. Understanding these is essential for both normal operations and debugging.

InputTypeDefaultEffect
loginbooleanfalseLog in to the Access Group portal. Required for guide PDF downloads. Public help-centre articles do not require login.
deepbooleantrueHarvest the full text of every article (not just the PDF). Creates richer index entries for articles that have no downloadable PDF.
guidesbooleantrueDownload the Salesforce-hosted guide PDFs in addition to the standard help-centre crawl.
guides_onlybooleanfalseSkip the help-centre loop entirely and only harvest guide PDFs. Much faster (~20 min vs ~2 hr). Use when guide PDFs are the only thing that has changed.
limitstring"0"Max articles per help centre. 0 = no limit. Use a small number (e.g. "3") for test runs.
print_fallbackbooleantrueWhen an article has no downloadable PDF, render the page to PDF using Playwright's print function.
diagnosticbooleanfalseSafe mode. Forces --no-login --guides-only --limit 1 --output downloads_diag. Skips index build and commit. Uploads only to downloads_diag/. Use this for any exploratory or debugging run - it physically cannot touch production data.
✓

Use diagnostic mode liberally. It was designed specifically to allow safe experimentation. Running with diagnostic=true costs only compute time and cannot corrupt any data. Always start here when something seems wrong.

Section 9

The Guide PDF Journey

This section documents the complete history of attempts to harvest the PeopleXD guide PDFs. It is written in detail because the root cause was non-obvious and the failures produced misleading-looking success signals at multiple points.

The problem

Access Group publishes detailed step-by-step user guides for each PeopleXD module. These are listed in "guide index" articles on the Intercom help centre, but the links in those articles do not point to Intercom - they point to accessgroup.my.salesforce.com. This distinction took months to identify clearly.

Attempt 1 - Wrong CSS selector

29 June 2026

The scraper used article table td:first-child a[href] to find links in guide index articles. The assumption was that the guide links would be in a table, as they were in a different part of the portal. Intercom does not render tables - it renders lists. The selector found zero links. The scraper reported success (no errors) but downloaded nothing.

✕

Lesson: A zero-result run that reports success is a silent failure. Always verify the count of downloaded files or manifest rows after any harvest, not just the workflow status.

Attempt 2 - Wrong URL filter

29 June 2026

The selector was broadened to article a[href] - every link in the article body. This found links, but the filter then restricted to URLs containing /articles/ in the path. The scraper found exactly 5 links per module - which seemed plausible. In reality, these 5 links were cross-references at the bottom of each guide index article pointing to the other guide index pages. The actual guide links pointed to Salesforce and were filtered out.

✕

Lesson: A plausible-looking result count is not a correct result. 5 links per module looked like "5 featured guides" - it was coincidental. Always inspect what the links actually are, not just how many there are.

Root cause identified

6 July 2026

A diagnostic run with detailed logging confirmed: all real guide links use the domain accessgroup.my.salesforce.com with paths like /sfc/p/{orgId}/a/{docId}/{hash}. There is no /articles/ in the path, no .pdf in the URL, and the domain is not theaccessgroup.com. Every previous filter rejected them.

Fix Part 1 - Domain filter

The filter was updated to accept accessgroup.my.salesforce.com as a valid link domain, alongside theaccessgroup.com and its subdomains. A separate set of normalised index page URLs (guide_index_url_set) was used to exclude cross-reference links that happen to also be on Intercom. A second diagnostic confirmed 310 guide links found across 11 modules.

Attempt 3 - Wrong download mechanism

Full harvest, July 2026

The domain filter was correct, but the download method was wrong. The scraper used context.request.get(url) - a direct HTTP request using the browser's session cookies. For Salesforce file viewer pages, this returns 200 OK with an HTML shell (the viewer UI), not the PDF file. The %PDF magic-byte check correctly detected this and rejected all downloads - resulting in 0 PDFs despite 310 links found.

✕

Lesson: A 200 OK response is not a PDF. Salesforce file viewer URLs return the viewer HTML when fetched directly, even with valid authentication cookies. The %PDF magic-byte check is essential - without it, HTML pages would have been saved as PDFs and silently indexed as garbage.

Fix Part 2 - Browser page navigation + download interception

7 July 2026 - PR #16

The correct approach: navigate the browser to the Salesforce viewer URL (page.goto(url)), wait for the page to render, find the Download button (button[title='Download']), and intercept the browser-triggered download event using Playwright's page.expect_download(). This is how a human would download the file, and it is the only way that works.

with page.expect_download(timeout=30_000) as dl_info:
    btn.click()
dl_info.value.save_as(str(dest))

A diagnostic run confirmed: 11/11 modules, 11 PDFs downloaded, 0 errors. The selector button[title='Download'] is consistent across every Salesforce file viewer page in the Access Group Community portal. The full harvest then ran cleanly: 307 PDFs downloaded, indexed, and committed.

✓

The pattern that works for Salesforce-hosted files: navigate the browser to the viewer page → wait for render → click the Download button → intercept with expect_download(). This generalises to any Salesforce Community file hosting, not just Access Group.

Section 11

What Was Ruled Out

These approaches were investigated and abandoned. Do not re-investigate them without a specific reason to believe circumstances have changed.

ApproachWhy ruled out
Microsoft Graph API Oxford IT policy blocks the AADSTS admin consent flow required for any Graph API app registration. All attempts - including PowerShell SDK - failed with the same AADSTS errors. This is an IT governance decision, not a technical limitation that can be worked around.
Chrome/browser extension for email access Too slow, too many tokens for the inbox size. COM automation via local script is more reliable and faster.
Outlook Restrict() with IncludeRecurrences for calendar Returns empty results on UK locale. Direct iteration over a date window is the only reliable approach for recurring calendar events in a UK-locale Outlook installation.
Direct HTTP fetch for Salesforce PDFs Salesforce file viewer URLs (/sfc/p/...) return an HTML viewer shell on direct HTTP request, even with valid session cookies. Browser navigation with page.expect_download() is required.
Vector/semantic search instead of BM25 Would require a server-side embedding store and API calls for every search - adding cost, latency, and infrastructure dependency. BM25 runs client-side with no cost and is fast enough for 2,500 documents. The retrieved context is passed to Claude for semantic understanding, so the retrieval step doesn't need to be semantic.

Diagnosing a failed harvest

  1. Check the workflow run logs in GitHub Actions - look for lines starting with Failed: or Error: in the scraper output, and download the artifact (includes errors.log).
  2. If 0 guide PDFs downloaded despite links found, check the SF landed: log lines - if it redirected to a login page, the Access Group session has expired or credentials are wrong.
  3. Run a diagnostic first: diagnostic=true, login=true. This is safe and gives fast feedback.
  4. Check data/kb.json document count before and after any run. If it dropped, a manifest was likely overwritten - restore from the last known good git commit.
!

If the document count drops after a run: do not run again. Check the git log for the last known good state (git log --oneline data/kb.json), restore the manifest from that commit, rebuild the index. Running again risks compounding the data loss.

Section 13

Recommendations for Expansion

Adding new data sources

The index builder (build_index.py) currently ingests: SharePoint exports, collection PDFs via manifest, and deep article text. Adding a new source means adding a new ingestion loop in build_index.py that reads from a folder or file, extracts text, and appends to the documents list before writing kb.json.

Candidate additional sources:

  • HR policy documents - if accessible as PDFs, drop them into a dedicated folder and add to the manifest
  • Recorded meeting notes - Granola or similar meeting AI transcripts exported to markdown, processed through the same BM25 chunking pipeline
  • Email threads - with appropriate anonymisation, common FAQ threads from IT support mailboxes
  • Release notes - Access Group release note PDFs (already partially captured by the help-centre scraper's cross-module section)

Adapting for a different HRIS vendor

The BM25 retrieval layer, the Cloudflare Worker, and the front end are all vendor-agnostic. Only the scraper (access_group_scraper.py) is specific to Access Group / Intercom / Salesforce. For a different vendor:

  • Identify the help documentation platform (Intercom, Zendesk, Confluence, custom)
  • Write a new scraper using the same Playwright skeleton - the download_salesforce_via_page() pattern is reusable for any Salesforce Community file hosting
  • Keep the same manifest format and index builder - the downstream pipeline is unchanged

Improving the retrieval layer

BM25 is excellent for known-terminology queries ("how do I configure pension by appointment"). It struggles with paraphrase or concept queries where the user's words do not match the document vocabulary. Options for improvement:

  • Hybrid retrieval - BM25 for keyword match, plus a small embedding model (e.g. running in a Cloudflare Worker via AI Gateway) for semantic re-ranking
  • Query expansion - send the user's query to Claude first to extract key terms and synonyms, then run BM25 on the expanded query
  • Chunk size tuning - the current chunking strategy in build_index.py uses fixed-size chunks; document-aware chunking (splitting at section boundaries) would improve context quality

Session renewal automation

The Access Group Salesforce session is tied to the scraper's login flow. Currently, if credentials change or the session policy tightens, the harvest silently fails (PDF check catches it). An improvement would be a pre-flight check step in the workflow that validates the session before starting the harvest proper, and fails fast with a clear error if authentication does not succeed.

Deploying for another department

The minimal viable deployment for a second department is:

  1. Fork the repo
  2. Point GUIDE_INDEX_ARTICLES at the new department's guide index articles
  3. Deploy a second Cloudflare Worker (or add a route to the existing one)
  4. Run the harvest

The front end (index.html) can be rebranded with minimal changes - the Oxford navy sidebar is a CSS variable (--navy: #002147) and the crest is an external image file. A new department can supply their own colours and logo.

i

Cost at scale: The system as built has near-zero ongoing cost (GitHub Pages free, Cloudflare Workers free tier). Claude API costs arise only on queries - at typical usage volumes for a team of 10-50, this is a few pounds per month. The only fixed cost is the self-hosted runner machine (which likely already exists as an admin workstation).

Cority (Health & Safety) - in progress

Cority is the University's Occupational Health / H&S management system - one of the first real tests of this pattern's "deploy for another department" claim. It turned out to have two independent content sources: a ClickHelp-hosted documentation portal requiring no login at all, and a Salesforce Experience Cloud community requiring the same email/password login pattern as Access Group. Both were confirmed technically viable through direct testing, including a genuine bulk-search API (Coveo) on the Salesforce side and a public sitemap on the ClickHelp side - in some respects an easier build than the original Access Group harvest, not harder.

i

Full findings: see CORITY-FEASIBILITY.md in begb0037admin/hr-fa-knowledge-base for the complete technical record - endpoints, login flow, a Salesforce image-authentication trap worth knowing about before it's copied into any other vendor build, and the recommended architecture. Feasibility confirmed 31 July 2026; build not yet started.
